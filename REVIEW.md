# REVIEW.md

Правила код-ревью для монорепо expense-tracker (`apps/api`, `apps/web`, `packages/shared`). Подробности по подпроектам — в [CLAUDE.md](CLAUDE.md), [apps/api/CLAUDE.md](apps/api/CLAUDE.md), [apps/web/CLAUDE.md](apps/web/CLAUDE.md).

Серьёзность замечаний: **blocker** — merge нельзя; **major** — исправить до merge; **minor** — желательно; **nit** — на усмотрение автора.

## 1. Процесс и Pull Request

- [ ] Ветка названа `<type>/<kebab-case-описание>` (`feat/main-screen`), создана от актуального `main`; прямых коммитов в `main` нет. **blocker**
- [ ] Одна ветка — одна задача, несвязанные изменения не смешаны.
- [ ] Коммиты следуют Conventional Commits: `<type>(<scope>): <описание>`, английский, повелительное наклонение, строчная буква, без точки, до ~72 символов; тело объясняет «почему».
- [ ] Breaking change помечен `!` и/или `BREAKING CHANGE:`.
- [ ] Title PR — по Conventional Commits; описание на русском по шаблону (Что сделано / Endpoints / Зачем / Breaking changes / Как проверить).
- [ ] `npm run build` зелёный (порядок: shared → api → web), `main` подтянут в ветку. **blocker**
- [ ] В коммиты не попали `.env`, `node_modules`, `dist`, `.next`, прочие артефакты и секреты. **blocker**
- [ ] Изменения `schema.prisma` и миграция лежат в одном коммите; изменения `packages/shared` — вместе с зависимыми правками `api`/`web`, если контракт ломается.
- [ ] Если изменились команды, архитектура, переменные окружения или состояние проекта — обновлены соответствующие `CLAUDE.md` (в том числе строки «Состояние» и «Тестов и линтера нет»).

## 2. Контракт `packages/shared`

- [ ] DTO и Zod-схемы для обмена фронт↔бэк живут только в `@expense/shared`; дублирования типов в `api`/`web` нет. **major**
- [ ] Типы выводятся из схем (`z.infer`), а не пишутся вручную параллельно.
- [ ] Изменение схемы обратно совместимо либо явно помечено как breaking и сопровождено правками `api` и `web`.
- [ ] Пакет остаётся CommonJS (`dist/` через `tsc`), в `dist` ничего не правится руками.

## 3. Backend (`apps/api`)

### Архитектура и CQRS
- [ ] Модули общаются только через CQRS (`@nestjs/cqrs`); прямых импортов `AuthModule` ↔ `UsersModule` и других модулей друг в друга нет. **major**
- [ ] Общие команды/запросы/события лежат в `src/contracts/`, handler'ы — внутри модуля-владельца данных.
- [ ] Пароль хэширует `auth` (`bcryptjs`), `users` хранит только `passwordHash`; хэш и пароль не попадают в ответы и логи. **blocker**

### Безопасность и доступ
- [ ] Новые эндпоинты (кроме `register`/`login`) закрыты `@UseGuards(JwtAuthGuard)`; `userId` берётся из `req.user.id`, а не из тела/параметров запроса. **blocker**
- [ ] Каждый запрос к данным фильтруется по владельцу; чужая сущность — 404 (не 403, чтобы не раскрывать существование). **blocker**
- [ ] Связанные сущности (категория при создании/смене транзакции, владелец категории) проверяются через соответствующие CQRS-запросы (`GetCategoryByIdQuery`, `GetUserByIdQuery`).
- [ ] Секреты (`JWT_SECRET` и др.) не захардкожены, читаются из окружения; API не стартует без `JWT_SECRET`.
- [ ] `@nestjs/cqrs` и `@nestjs/jwt` остаются на `^11`.

### Валидация и HTTP-контракт
- [ ] Тела запросов валидируются Zod-схемами из `@expense/shared` через `ZodValidationPipe`; query-параметры (`year`, `month`, `page`, `limit`) тоже проверяются и ограничены (`page` ≤ 100000, `limit` ≤ 100). **major**
- [ ] Коды ответов соответствуют принятым: чужая/несуществующая сущность — 404, дубликат — 409, удаление категории с транзакциями — 409, нет/просрочен токен — 401.
- [ ] Формат ответа `GET /transactions` не сломан: `{ items, summary, pagination }`, порядок `date desc, createdAt desc, id desc`, `summary` — по всему периоду (UTC), `amount` отдаётся как number.
- [ ] Списочные эндпоинты пагинируются, нет выборок «всё без limit».

### База данных (Prisma)
- [ ] Денежные суммы — `Decimal(12,2)`, не `Float`; конвертация в number происходит только на границе API.
- [ ] Уникальности и связи (`email`, `(userId, name)` у `Category`) сохранены; нужные индексы добавлены под новые запросы.
- [ ] Для изменения схемы есть миграция; она применима через `migrate deploy`, не ломает существующие данные (дефолты/backfill для новых NOT NULL-колонок). **blocker**
- [ ] После изменения схемы выполнен `prisma:generate`; Prisma-скрипты по-прежнему запускаются через `node --env-file=../../.env`.
- [ ] Нет N+1: связанные данные грузятся через `include`/агрегации, а не циклом запросов.

## 4. Frontend (`apps/web`)

### FSD
- [ ] Импорты идут только вниз: `app → views → widgets → features → entities → shared`. **major**
- [ ] Слайсы одного слоя не импортируют друг друга.
- [ ] Каждый слайс отдаёт публичный API через `index.ts`; глубоких импортов (`@/features/x/ui/...`) снаружи нет.
- [ ] Код лежит в правильном слое: бизнес-сценарий — `features`, сущность — `entities`, крупный блок — `widgets`, универсальное без бизнес-логики — `shared`.
- [ ] `app/**/page.tsx` тонкие: только `metadata` и реэкспорт из `views`. Слой назван `views`, не `pages`.
- [ ] Используется алиас `@/*`, без длинных относительных путей через слои.

### React / Next.js
- [ ] `'use client'` только там, где нужны хуки или обработчики; страницы `views` остаются серверными.
- [ ] Формы — `react-hook-form` + `zodResolver` со схемами из `@expense/shared`.
- [ ] Запросы к API идут через `apiFetch` (`shared/api`); ошибки обрабатываются через `ApiError`, 401 уходит в общий `setUnauthorizedHandler`.
- [ ] Адрес API берётся из `NEXT_PUBLIC_API_URL`, не захардкожен. В `NEXT_PUBLIC_*` нет секретов. **blocker**
- [ ] Сессия читается через `useSession` (`entities/session`), ключ `expense.session` не используется напрямую вне слайса.
- [ ] Защищённые страницы лежат в `app/(protected)` под `RequireSession`; клиентская защита не считается заменой серверной авторизации.
- [ ] Есть состояния загрузки, ошибки и пустого списка; деньги и даты форматируются через `formatMoney` / `formatDate`.

### UI и стили
- [ ] Компоненты shadcn/ui (стиль `new-york`) добавлены через `npx shadcn@latest add`, лежат в `shared/ui`, вручную не форкаются без причины.
- [ ] Tailwind v4 CSS-first: токены в `globals.css`, `tailwind.config` не создаётся; классы собираются через `cn`.
- [ ] Базовая доступность: `label` у полей, осмысленные тексты кнопок, фокус и клавиатура работают.

## 5. Качество кода

- [ ] TypeScript strict: нет `any`, `@ts-ignore`, необоснованных `as`-приведений и `!`.
- [ ] Нет мёртвого кода, закомментированных блоков, отладочных `console.log`.
- [ ] Обработка ошибок на границах (HTTP, БД, `localStorage`); ошибки не глотаются молча.
- [ ] Имена на английском, понятные; комментарии объясняют «почему», а не «что».
- [ ] Форматирование соответствует Prettier (`npm run format`), в диффе нет шума от переформатирования.
- [ ] Новые зависимости обоснованы, версии совместимы со стеком (Next 15, React 19, NestJS 11); скрипты Prisma остаются в `allowScripts`.

## 6. Тесты и верификация

Автотестов и линтера в проекте пока нет, поэтому:

- [ ] В описании PR есть конкретные шаги ручной проверки и результат `npm run build`.
- [ ] Для api-изменений указаны проверенные эндпоинты и коды ответов (в том числе негативные: 401, 404, 409, 400).
- [ ] Если в PR добавляются тесты или линтер — обновлены раздел «Команды» и строки «Тестов и линтера нет» в `CLAUDE.md`.

## 7. Что не считается замечанием

- Отсутствие тестов и ESLint само по себе (они запланированы отдельно).
- Заглушки `/transactions` и `/categories`, отсутствие UI создания категорий — известные ограничения.
- Клиентское хранение сессии в `localStorage` — принятое на данный момент решение; замечание уместно только при появлении XSS-рисков (например, `dangerouslySetInnerHTML`).
- Файлы миграций Prisma (`prisma/migrations/**`)
- `package-lock.json` и другие lock-файлы
- `*.log` файлы
